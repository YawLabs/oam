# The oamjs npm packages

The second distribution channel for oam, beside `install/`. Nothing here has
been published: `npm view oamjs` is a 404 today, and so is every
`oamjs-<platform>-<arch>` name below.

`curl https://oamjs.org/install.sh | sh` asks someone to pipe a script from a
domain they have never heard of into their shell. `npx oamjs script.ts` asks
them for nothing they do not already do daily, and an npm dependency is
something a team can pin in the lockfile they already have.

## Why `npm/` and not somewhere else

Beside `install/`, which holds the other channel. Not under `js/`: that tree is
the runtime's own JavaScript and `crates/oam_engine/build.rs` compiles it into
the V8 startup snapshot, so a packaging file dropped there is at best confusing
and at worst something the snapshot tries to eat. Not under `crates/`: nothing
here is Rust and nothing here is a cargo member.

## Shape

```
npm/oamjs/                 the launcher -- the only package a user names
npm/oamjs-win32-x64/       one per published target, binary only
npm/oamjs-win32-arm64/
npm/oamjs-darwin-x64/
npm/oamjs-darwin-arm64/
npm/oamjs-linux-x64/
```

The launcher declares all five as `optionalDependencies` with exact version
pins. npm installs only the one whose `os` / `cpu` match the host and skips the
rest, so a Mac user downloads one 60 MB binary rather than five. At run time
`npm/oamjs/lib/resolve.js` does `require.resolve('oamjs-darwin-arm64/bin/oam')`
and exec's what comes back.

**There is no `postinstall` script, deliberately.** A postinstall that downloads
a binary is the shape the ecosystem defaults to, and it is the shape oam argues
against everywhere else: `oam trust` and OAM-PKG0007 exist because arbitrary
code running at install time is a supply-chain problem, and shipping one here
would say the opposite of what the runtime says. It also fails behind
proxies, in offline CI and in any sandbox with no network at install time, none
of which affects an ordinary tarball.

The cost of that choice is honest and worth naming: every platform tarball is a
full ~60 MB binary, and npm's registry, not a CDN redirect, serves it.

### aarch64-unknown-linux-gnu

There is no Linux ARM binary. The V8 startup snapshot must be generated by a
process of the target architecture (`crates/oam_engine/build.rs`), so it cannot
be cross-compiled, and no ARM Linux build host has ever been in the release
loop. So no `oamjs-linux-arm64` package exists, and the launcher says so in the
same words `install/install.sh` uses rather than letting npm report a missing
optional dependency -- which would blame the user's install for a binary that
was never built.

## Versioning

`npm/sync-packages.mjs` derives all six manifests from two sources: the
`[workspace.package] version` in `Cargo.toml`, and the platform table in
`npm/oamjs/lib/targets.js`. Nothing under `npm/` carries a hand-maintained
version.

```sh
node npm/sync-packages.mjs           # rewrite the manifests
node npm/sync-packages.mjs --check   # exit 1 on drift, write nothing
```

`--check` is the detection. It also runs as a test (`npm/test/sync-packages.test.mjs`),
so the npm test suite fails the moment `release-local.sh` bumps the
workspace version without a re-sync. Wiring `--check` into `scripts/ci-local.sh`
as its own step is the remaining piece -- see "Not wired yet" below.

## Testing

```sh
node --test "npm/test/*.test.mjs"     # or: cd npm && npm test
```

No dependencies, no install step: `node:test` and a fixture that stands in for
the oam binary. The launcher tests drive the real `bin/oamjs.js` against a real
child process, because the claims it makes -- byte-exact stdio, faithful exit
status, forwarded signals -- are claims about the operating system, and a
mocked `spawn` would only prove the launcher agrees with itself.

One case, the end-to-end POSIX SIGTERM test, self-skips on Windows and says so.
The Windows branch of the same code is covered with an injected platform.

## Local verification (no publish)

```sh
mkdir /tmp/rel
cp target/release/oam.exe /tmp/rel/oam-aarch64-pc-windows-msvc.exe   # your target
cp LICENSE NOTICE THIRD_PARTY_LICENSES.md /tmp/rel/

node npm/sync-packages.mjs --check
node npm/stage.mjs /tmp/rel --only oamjs-win32-arm64
( cd npm/oamjs-win32-arm64 && npm pack --pack-destination /tmp/rel )
( cd npm/oamjs && npm pack --pack-destination /tmp/rel )

mkdir /tmp/try && cd /tmp/try && npm init -y
npm install /tmp/rel/oamjs-win32-arm64-*.tgz /tmp/rel/oamjs-*.tgz
./node_modules/.bin/oamjs --version
./node_modules/.bin/oamjs -pe "2+2"
```

`--only` is for exactly this. A release must stage all five.

## Publishing (not wired -- what the release step would need)

`scripts/release-local.sh` is deliberately not touched by this change. When it
is wired, the step belongs immediately after "Stage license + attribution
alongside the binaries", where `$RELEASE_DIR` holds all five binaries plus
`LICENSE`, `NOTICE` and `THIRD_PARTY_LICENSES.md` -- which is exactly what
`npm/stage.mjs` consumes:

```sh
node npm/sync-packages.mjs --check || fail "npm manifests are stale for $TAG"
node npm/stage.mjs "$RELEASE_DIR"

# Per-platform packages FIRST, launcher LAST. The launcher pins exact versions;
# publishing it before its binaries exist means every install in that window
# resolves nothing and skips the optional dependency silently.
for p in oamjs-win32-x64 oamjs-win32-arm64 oamjs-darwin-x64 oamjs-darwin-arm64 oamjs-linux-x64; do
  ( cd "npm/$p" && npm publish --access public )
done
( cd npm/oamjs && npm publish --access public )
```

Notes for whoever wires it:

- **Gate it on the tag, and on `--dry-run` first.** `npm publish --dry-run`
  prints the file list; a platform package whose list has no `bin/` entry is a
  staging failure and must not be published. npm allows unpublish only within
  72 hours, and never a re-publish of the same version.
- **Auth is the same automation token the other @yawlabs packages publish
  with.** There is no GitHub Actions here (decision D5), so npm provenance
  (`--provenance`, which needs a CI OIDC token) is not available; say nothing
  about provenance rather than implying it.
- **The npm publish is not idempotent with the GitHub release.** A release that
  uploads assets and then fails at `npm publish` leaves the two channels at
  different versions. Publishing last, after `gh release create` succeeds, makes
  the failure "npm is one version behind" rather than "npm points at a release
  that does not exist".
- **Five separate `npm publish` calls, not a workspace publish.** These are not
  npm workspaces (no root manifest lists them), on purpose: a workspace root
  would put a `package.json` at the repo root of a Rust project.

## Not wired yet

- `scripts/ci-local.sh` does not run `node npm/sync-packages.mjs --check` or the
  npm tests. It should, as a cheap non-compiling step next to step 11.
- `README.md` and `install/README.md` still describe the npm package as planned
  under `@yawlabs/oam` and as "a thin postinstall wrapper". Both are wrong now:
  the name is `oamjs` and there is no postinstall. A docs pass owns those files.
- Nothing is published. The names are unregistered.

## Windows: stop the server by closing stdin, not by killing the PID

On POSIX the launcher forwards `SIGINT`, `SIGTERM`, `SIGHUP`, `SIGQUIT`,
`SIGUSR1` and `SIGUSR2` to oam and then reproduces the child's death, so an MCP
host that stops a server by killing the PID it spawned gets the behaviour it
expects.

Windows has no equivalent. A PID-directed kill there is `TerminateProcess`,
which runs no JavaScript and does not touch descendants: the launcher dies
instantly and `oam.exe` keeps running with the host's stdio handles open. The
host may never see EOF on the pipe it was reading, and each restart leaks
another runtime process.

There is no fix available to this package. Node cannot exec-replace itself, and
containing a process tree on Windows needs a job object, which needs a native
addon -- and this package ships no postinstall and no build step by design.

So on Windows, stop an oam-hosted MCP server by **closing its stdin**, which oam
handles as a clean shutdown, rather than by killing the launcher's PID.
