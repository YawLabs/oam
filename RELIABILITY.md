# Reliability Program — the scorecard is the product

"Fewer bugs than Bun" must be a dashboard, not a slogan. This file defines what oam measures,
publishes, and gates releases on. The receipts live in the repo and are never
hand-edited: CONFORMANCE.md and CONFORMANCE-NODE.md are regenerated by
`scripts/ci-local.sh` on every gate run, and BENCHMARKS.md by a separate, manual
`cargo run -p xtask -- bench --release --compare` -- no gate or release script
runs the benchmarks, so BENCHMARKS.md describes the commit and oam version it
is stamped with, not necessarily the current release. There is no hosted
dashboard yet; when there is, it will be on oamjs.org, which is the project's
domain.

## Published metrics

This is the program, not a claim that all of it runs today. The Status column
says which rows have something behind them in this tree and which are still
plans; a row marked planned has no harness, tool or data yet.

## Semver policy

- **Pre-1.0:** every release ships a public behavior-change log: every observable change
  (API, CLI flags, defaults, error text) enumerated. Today that log is CHANGELOG.md, written
  by hand; generating it with an API-diff bot plus human annotation is planned, and no such
  tool exists yet. The discipline starts now; the hard gate starts at 1.0.
- **From 1.0 (mechanical semver):** a versioned snapshot of the public surface (runtime
  `.d.ts`, CLI flags, behavior matrix including defaults) is checked in; CI diffs every PR
  against it. Any observable change requires a major version. No exceptions, no "minor
  cleanup" carve-outs — those are how trust dies in patch releases.
- **N-1 gate (planned):** every release must pass the previous release's entire test suite.
  No release step runs the previous release's suite today. Tests may
  not be modified in the same PR as the implementation they gate (AI-POLICY.md gate 3).

## LTS

Committed now, effective at 1.0: every 1.x line is maintained for 24 months from its 1.0.
Details (cadence of LTS lines after 2.0) will be specified before 1.0 ships.

## Platform policy

Tier-1 is the five targets that ship binaries: windows-x64, windows-arm64, macos-x64,
macos-arm64, linux-x64-gnu. "Tested on Windows before it ships, not after." They are not all
gated at the same moment, and none by a hosted per-PR CI:

- **windows-arm64** is the daily dev target: the full gate (`scripts/ci-local.sh`, also the
  pre-push hook) runs there on every change.
- **windows-x64, macos-x64, macos-arm64, linux-x64-gnu** are built and tested by the remote
  and emulated legs of `scripts/release-local.sh`, so they are gated per release, not per PR
  (CONTRIBUTING.md describes the legs).

linux-arm64-gnu is a goal, not a tier-1 target today: it builds from the same tree but has
never been built for release or gated, because the V8 snapshot forbids cross-compiling and
there is no native ARM Linux builder yet.

## Fuzzing

Planned; no fuzz target exists in the tree yet. The intended targets are the Rust<->V8 ops
boundary, lockfile/package.json parsers, HTTP parsing, and the TS stripper, run continuously,
with an OSS-Fuzz application and published trophies to follow.

## oam's own supply chain

From v0.18.0 every release carries `RELEASE-MANIFEST` (the tag plus the `SHA256SUMS` lines)
and `RELEASE-MANIFEST.sig`, signed with release key k1; see SECURITY.md, "Release integrity",
for the fingerprints. The installer scripts are served from oamjs.org. They, and
`oam self-update`, verify that signature against the release keys embedded in them
(`release-keys/`) and refuse to install a binary whose hash does not match the signed
manifest. The installers need `ssh-keygen` with `-Y` (OpenSSH 8.1+); releases before v0.18.0
are checked against pinned `SHA256SUMS` digests instead. The Windows binaries are
Authenticode-signed through Azure Artifact Signing, as "Yaw Labs LLC". The macOS binaries
are signed with oam's own pinned, self-signed identity and the hardened runtime; Apple
Developer ID signing and notarization, SLSA provenance and reproducible builds are planned,
not yet in place.
