## Deliberate divergences (counted as failures above)

These fail on purpose and are expected to keep failing. They are NOT skipped: each one runs, counts as a failure, and stays in the denominator, so the pass rate above is unaffected by this section existing. Listed separately only so a settled decision is not mistaken for untriaged work.

- `test-buffer-backing-arraybuffer.js` -- [exit=1] oam:node_compat.js:7689
  - A V8-VERSION divergence, not an oam gap -- the only entry here that is about the engine underneath oam rather than about oam. The test reads internalBinding('util').arrayBufferViewHasBuffer (V8's ArrayBufferView::HasBuffer: whether the view's backing ArrayBuffer OBJECT has been materialized yet) and asserts a table that is a V8 12 implementation detail -- expectOnHeap true, i.e. hasBuffer FALSE, at lengths 0 and 48, and hasBuffer TRUE at 96 and 1024, for Uint8Array / Uint16Array / Uint32Array / Float32Array / Float64Array / Buffer.alloc / Buffer.allocUnsafeSlow alike. Measured on this machine: real node v22.22.2 (V8 12.4.254.21-node.39) reproduces that table exactly and exits 0; oam links V8 15.0.245.2, which no longer allocates small typed arrays on the V8 heap, so every live ArrayBufferView genuinely HAS a buffer and the op answers true at all four lengths -- oam fails on the first case ('mismatch: false vs true for Uint8Array, length = 0'). oam's op (crates/oam_engine/src/node_ops.rs, op_array_buffer_view_has_buffer) is a wrapper over v8::ArrayBufferView::has_buffer() and reports the linked V8's answer faithfully: it is CORRECT, and it is the test's expectation that has expired. Passing would mean answering false for a buffer that demonstrably exists -- inventing a heap layout this V8 does not have -- and it would then contradict the test's own consistency check two lines further on, which reads .buffer and asserts hasBuffer is now true. Nothing in oam should change to chase it, and the test comes back by itself if V8 ever reintroduces on-heap typed arrays. Recorded as divergence 31 in docs/node-divergences.md. FOR REVIEW: this entry is why maxDeliberate moved 2 -> 3.

- `test-process-versions.js` -- [exit=1] oam:node_compat.js:7689
  - Asserts a strict deep-equal on the process.versions KEY SET -- an ARRAY compare, so both membership and order are load-bearing. After common/index.js gates the optional groups, what the test still demands of oam is 'acorn', 'ares', 'cjs_module_lexer', 'llhttp', 'nbytes', 'nghttp2', 'simdjson', 'simdutf', 'uv', 'uvwasi', 'zlib', 'zstd' plus Node's own ABI counters 'modules' and 'napi' -- C libraries oam does not link and version numbers for an ABI it does not implement. It does NOT demand 'openssl'/'ncrypto', 'icu'/'cldr'/'tz'/'unicode', 'sqlite', 'ngtcp2'/'nghttp3', 'undici' or 'amaro': each of those groups suppresses its own requirement, because the test appends them only behind a common/index.js predicate derived from the very surface oam omits (index.js:54 hasCrypto = Boolean(process.versions.openssl); index.js:37 hasIntl = !!process.config.variables.v8_enable_i18n_support; hasSQLite, hasQuic, hasUndici and hasAmaro the same way). The compare also fails in the other direction, which is the part that cannot be fixed by adding keys: oam publishes the dependency tree it ACTUALLY builds against, generated from Cargo.lock at build time (v8, tokio, hickory, rustls, ring, oxc, hyper, brotli, flate2, icu, url, ada, h2, reqwest, unicode), and every one of those beyond the four the sets share -- 'node', 'v8', 'brotli', 'ada' -- is an extra key the deep-equal rejects. Passing would mean deleting the real names and inventing the absent ones, i.e. having process.versions state something false about the binary. The honest surface is worth more than the test.

## Partial skips (scored by exit code, INSIDE the denominator)

Each of these prints a TAP `1..0 # Skipped` marker part-way through -- `common.printSkipMessage()` does not exit -- and then keeps asserting to the end of the file, so the marker does not describe how the run ended. For these the marker is ignored and the exit code decides, which lands them in pass or fail above instead of the self-skipped list below. No output-only rule can tell such a test from one that `common.skip()`s at the top and asserts nothing (their stdout is byte-identical), so this is a per-file manifest opt-in, ratcheted by `maxPartialSkips`, not a heuristic.
