## Deliberate divergences (counted as failures above)

These fail on purpose and are expected to keep failing. They are NOT skipped: each one runs, counts as a failure, and stays in the denominator, so the pass rate above is unaffected by this section existing. Listed separately only so a settled decision is not mistaken for untriaged work.

- `test-buffer-backing-arraybuffer.js` -- [exit=1] AssertionError [ERR_ASSERTION]: mismatch: false vs true for Uint8Array, length = 0
  - A V8-VERSION divergence, not an oam gap -- the only entry here that is about the engine underneath oam rather than about oam. The test reads internalBinding('util').arrayBufferViewHasBuffer (V8's ArrayBufferView::HasBuffer: whether the view's backing ArrayBuffer OBJECT has been materialized yet) and asserts a table that is a V8 12-14 implementation detail -- expectOnHeap true, i.e. hasBuffer FALSE, at lengths 0 and 48, and hasBuffer TRUE at 96 and 1024, for Uint8Array / Uint16Array / Uint32Array / Float32Array / Float64Array / Buffer.alloc / Buffer.allocUnsafeSlow alike. Measured on this machine: real node v26.13.1 (V8 14.6.202.34-node.40) reproduces that table exactly and exits 0, as v22.22.2 (V8 12.4.254.21-node.39) did; oam links V8 15.0.245.2, which no longer allocates small typed arrays on the V8 heap, so every live ArrayBufferView genuinely HAS a buffer and the op answers true at all four lengths -- oam fails on the first case ('mismatch: false vs true for Uint8Array, length = 0'). oam's op (crates/oam_engine/src/node_ops.rs, op_array_buffer_view_has_buffer) is a wrapper over v8::ArrayBufferView::has_buffer() and reports the linked V8's answer faithfully: it is CORRECT, and it is the test's expectation that has expired. Passing would mean answering false for a buffer that demonstrably exists -- inventing a heap layout this V8 does not have -- and it would then contradict the test's own consistency check two lines further on, which reads .buffer and asserts hasBuffer is now true. Nothing in oam should change to chase it, and the test comes back by itself if V8 ever reintroduces on-heap typed arrays. Recorded as divergence 31 in docs/node-divergences.md.
- `test-process-binding-internalbinding-allowlist.js` -- [exit=1] Error: No such module: buffer
  - Asserts the legacy process.binding names are truthy: on v26.13.1, 19 unconditionally plus 'icu' (common.hasIntl is true on oam), with 'tls_wrap' gated off by hasCrypto; the first, 'buffer', already throws on oam. oam models the ones it can back with the REAL implementation (constants, util, tty_wrap.isTTY) taken by identity off the public surface, and THROWS for the rest -- mostly libuv handle classes (TCP, UDP, Pipe, JSStream, FSEvent) it has nothing behind. Returning {} would claim them, and it is also worse for the caller than throwing: a package that feature-detects process.binding('tcp_wrap'), gets an empty object and proceeds hits a TypeError deep in its own code, where the throw sends it straight to the fallback branch that is correct for oam. See js/node_compat.js (process.binding).
- `test-process-versions.js` -- [exit=1] AssertionError [ERR_ASSERTION]: Expected values to be strictly deep-equal:
  - Asserts a strict deep-equal on the process.versions KEY SET -- an ARRAY compare, so both membership and order are load-bearing. Measured on v26.13.1 against oam: after common/index.js gates the optional groups, the test demands of oam 'acorn', 'ares', 'llhttp', 'merve', 'nbytes', 'nghttp2', 'nghttp3', 'ngtcp2', 'simdjson', 'simdutf', 'uv', 'uvwasi', 'zlib' plus Node's own ABI counters 'modules' and 'napi' -- C libraries oam does not link and version numbers for an ABI it does not implement -- and, because common.hasIntl is true on oam (index.js:37, process.config.variables.v8_enable_i18n_support: V8's ICU is real), 'cldr' and 'tz' as well, versions that live in ICU data files oam cannot verify. It does NOT demand 'openssl'/'ncrypto', 'sqlite', 'libffi', 'undici', 'amaro' or 'lief': each of those groups is appended only behind a predicate derived from the very surface oam omits (index.js:69 hasCrypto = Boolean(process.versions.openssl); hasSQLite, hasFFI and the node_builtin_shareable_builtins / node_use_lief config checks the same way). The compare also fails in the other direction, which is the part that cannot be fixed by adding keys: oam publishes the dependency tree it ACTUALLY builds against, generated from Cargo.lock at build time (v8, tokio, hickory, rustls, ring, oxc, hyper, brotli, flate2, icu, url, ada, h2, reqwest, unicode, zstd), and every one of those beyond the seven the sets share -- 'node', 'v8', 'ada', 'brotli', 'icu', 'unicode', 'zstd' -- is an extra key the deep-equal rejects. Passing would mean deleting the real names and inventing the absent ones, i.e. having process.versions state something false about the binary. The honest surface is worth more than the test.

## Partial skips (scored by exit code, INSIDE the denominator)

Each of these prints a TAP `1..0 # Skipped` marker part-way through -- `common.printSkipMessage()` does not exit -- and then keeps asserting to the end of the file, so the marker does not describe how the run ended. For these the marker is ignored and the exit code decides, which lands them in pass or fail above instead of the self-skipped list below. No output-only rule can tell such a test from one that `common.skip()`s at the top and asserts nothing (their stdout is byte-identical), so this is a per-file manifest opt-in, ratcheted by `maxPartialSkips`, not a heuristic.
